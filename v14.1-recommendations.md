# GSL Simulator v14.1 Recommendations

Prepared after pulling `gsl-elevation-simulator` into `/Users/nephiharvey/Documents/Bob GSL` and reviewing the private v14 planning dossier, extracted addenda, and current `gsl-simulator-v14.html`.

## Executive Recommendation

v14.1 should be a hardening and credibility release, not a broad redesign. v14 already made the correct architectural move: it rebuilt from the v10.4 visual/model baseline and selectively ported v12 concepts. The next version should close the remaining scientific and implementation gaps that would undermine confidence in public or expert review.

Priority order:

1. Extend the model horizon consistently to 2036.
2. Make year-by-year accounting editable or explicitly scenario-driven.
3. Separate ENSO/atmospheric-river event forcing from the old ENSO-as-time-constant shortcut.
4. Refresh and timestamp live/current climate and lake inputs.
5. Recreate the Perplexity-origin figures in the simulator style.
6. Add validation checks proving controls actually move forecasts.
7. Add an internal maintenance guide for future human and AI contributors.

## Data and Research Boundary

v14.1 can be built from scratch as an application update using the material already in the repository: v10.4/v14 model code, embedded historical GSL elevation/volume arrays, GSLST and USGS budget tables, extracted Markdown, white-paper text, and the attached reference figures.

It should not invent new scientific coefficients from those materials alone. For current climate state, calibration coefficients, or claims intended for scientific review, v14.1 should use fresh official or primary sources. The minimum current-data refresh should include USGS Saltair elevation, NOAA CPC ENSO discussion and strength probabilities, and NOAA/NCEI ERSST v5 PDO. Any atmospheric-river multiplier calibration should be treated as a research task using a vetted atmospheric-river catalog, not as something the static simulator "discovers" live in a browser.

Practical boundary:

- Build now from local code and vetted attached documents.
- Refresh official current-status data before each shareable draft.
- Use provisional coefficients only when labeled as provisional.
- Do not embed live calibration routines unless the source dataset, method, and review status are explicit.

## Highest-Priority v14.1 Changes

### 1. Make 2036 a first-class horizon

The planning dossier asks for a 2036 extended risk horizon, but v14 still keeps primary forecast arrays at 2025-2034:

- `FCST_YEARS`
- `BASELINE`
- `FCST_CI`
- Tarboton mean and percentile arrays
- combined-model comparison text and chart titles
- Overview and Simulator KPI labels

v14.1 should extend every forecast-facing array, label, report, and uncertainty band to 2036. The 2034 Olympic marker should remain, but 2036 should become the explicit extended-risk endpoint. The uncertainty cone should widen further by 2036 rather than recycling the 2034 confidence posture.

Recommended UI: show both `2034 milestone` and `2036 risk horizon` KPI cards.

### 2. Promote annual accounting from read-only presets to controlled scenario inputs

v14 fixed the v12 bug where annual tables were decoration, but the table is still read-only. That is acceptable for v14 private draft; it is too limiting for 14.1.

Recommended 14.1 behavior:

- Keep sliders as coarse scenario builders.
- Let users edit annual kAf values in the table.
- Mark edited cells as manual overrides.
- Recompute all downstream forecast series immediately.
- Add a reset button per lever and for the full table.
- Preserve lever-type rules: recurring, wet-year dependent, one-time, ramp/buildout, structural baseline.

This is especially important for Newfoundland, reservoir releases, ag leasing, and other episodic/conditional sources where annual availability is the whole policy question.

### 3. Split ENSO/atmospheric-river forcing from the legacy time-constant shortcut

v14 text correctly says ENSO should work through atmospheric-river delivery, but the engine still uses:

```text
tau_eff = tau_slow_base * (1 - 0.1 * ENSO)
P_eff = (P_climate - 830) * (1 + ENSO * 0.12)
```

That is a reasonable inherited shortcut, but it is no longer aligned with the paper. v14.1 should introduce an explicit climate-event layer:

```text
pdoPhase -> atmospheric bridge modifier
ensoState -> atmospheric-river event probability / intensity
snowFraction -> capture efficiency
precipSignal(year) -> routed lake response after lag
```

Keep the old tau adjustment as a compatibility option or remove it after side-by-side comparison. The user-facing explanation and code path should not disagree.

### 4. Refresh current data and timestamp assumptions

The dossier's official-data check was made on 2026-05-21. As of the NOAA CPC ENSO Diagnostic Discussion issued 2026-05-14, ENSO-neutral conditions continued, an El Nino Watch was active, El Nino was likely by May-July 2026 at 82%, and the next discussion was scheduled for 2026-06-11. The May 2026 CPC strength table still showed peak-strength uncertainty, with no category above 37%.

v14.1 should add an in-app `Data Vintage` block:

- USGS Saltair elevation value and timestamp.
- CPC ENSO discussion issue date.
- CPC strength table issue month.
- NCEI PDO latest complete month.
- Whether the model is using live values or fallback constants.

This keeps the simulator honest when a "current PDO/ENSO" statement becomes stale.

### 5. Recreate the embedded figures

v14 embeds Perplexity-origin PNGs for private use. v14.1 should recreate the most important figures with local data/code and consistent visual styling where the underlying data are available:

- PDO lag verification.
- PDO-GSL lag/correlation sensitivity.
- Snow-fraction correction.
- PDO x ENSO atmospheric-river multiplier matrix.
- Lag-corrected stochastic fan with Stage 1 and Stage 2 windows.

The 2020-2060 recharge-opportunity schematic is dangerous as a forecast graph. It can make near-term forecast-window predictions look equivalent to long-range "crystal ball" speculation. In v14.1, it should be recast as a regime-opportunity/risk schematic only:

- No lake-elevation forecast line beyond the validated model horizon.
- No visual style matching the RC/Tarboton forecast cone.
- Use broad shaded windows for possible PDO flip timing, drought-risk periods, and replenishment-opportunity periods.
- Label it "conceptual regime timing, not an elevation forecast."
- Keep it in Model & Methods or an appendix, not in the main Simulator or Cross-Validation forecast panels.

The intent is useful: show probable ranges where PDO transitions might create either drought risk or replenishment opportunity. The implementation must not imply forecast-grade precision beyond the model's skill window.

Apply the same principle to any bar chart or timing chart that mixes known and speculative windows:

- Observed/current PDO/ENSO windows should use one visual treatment.
- Forecast-window assumptions should use a second treatment.
- Provisional scenario windows should use a third treatment.
- Conceptual long-range regime windows should be visually distinct from all forecast-grade elements.
- Legends and captions should say which category is observed, forecast, provisional, or conceptual.

### 6. Tighten scientific claims and citations

The Markdown critique is already careful, but v14 still contains a few claims that deserve stronger guardrails before wider sharing:

- Do not say "current PDO is -4 sigma"; say PDO reached -4.21 in July 2025 and remained negative in latest official 2026 data.
- Label atmospheric-river multipliers `x1.8` and `x3.2` as provisional until calibrated against an atmospheric-river catalog.
- Present the 2029-2031 bump as a required self-consistency check for the current RC plus PDO/ENSO interaction framing, while still showing uncertainty around its size and timing. The model should not fabricate a bump, but absence of any lagged response should trigger review.
- Explain 3-year, 6-year, 7-8-year, and 9.3-year lags in one canonical table and reuse that wording everywhere.
- Avoid "PDO forcing" except when clearly referring to a model abstraction.

The canonical lag table already exists in the original planning materials and should be promoted into the app/white paper as the single source of wording.

### 7. Atmospheric-river calibration policy

Do not embed live atmospheric-river multiplier calibration in the static v14.1 app. Atmospheric-river calibration is a diagnostic tool. The app can expose provisional atmospheric-river multipliers and scenario controls, but calibration should be performed offline from a documented atmospheric-river catalog and then imported as reviewed coefficients after Prof. Chikamoto review.

Recommended structure:

- `ATMOSPHERIC_RIVER_MULTIPLIERS_PROVISIONAL` in code, visibly labeled.
- A separate citation/method note explaining the current coefficient source.
- A future `calibration/` script or notebook for expert-reviewed updates, outside the public simulator UI.
- A UI badge showing `provisional`, `reviewed`, or `calibrated` status.

### 8. Add verification tests

v14.1 should include a small test/QA harness, even if the app remains a single static HTML file. Minimum checks:

- Overview conservation changes the forecast and KPI.
- Overview augmentation changes the forecast and KPI.
- Every Simulator lever changes the annual table and forecast.
- Editing an annual value changes the forecast.
- Newfoundland does not recur indefinitely unless the scenario explicitly includes refill or partial refill, such as a 2026-27 El Nino recharge assumption.
- Structural gain is displayed but not double-counted.
- 2036 uncertainty is wider than 2034 uncertainty.
- Live-data failure falls back gracefully.
- Cross-Validation chart updates after scenario changes.
- Preserved tabs render after model changes.

### 9. Add contributor guardrails

v14.1 should include both lightweight code comments and a standalone maintenance guide for future humans and AI tools. The goal is not to narrate every line, but to mark the model invariants that should not be casually changed.

Recommended file: `AI-MAINTENANCE-GUIDE.md`.

Include:

- Non-negotiable scientific guardrails: datum, baseline source, PDO-as-indicator language, lag table, provisional atmospheric-river multipliers.
- Implementation invariants: one shared forecast engine, annual accounting must drive the graph, structural gains must not be double-counted, 2034 and 2036 have different meanings.
- Source hierarchy: official data first, local reviewed documents second, generated figures last.
- Required checks before changing forecast logic.
- How to update citations and AI assistance language.

## Suggested v14.1 Scope

Keep v14.1 narrow:

1. Data vintage/status panel.
2. 2036 horizon completion.
3. Editable annual accounting overrides.
4. Explicit ENSO/PDO/atmospheric-river scenario engine.
5. In-code recreated figures for the white paper.
6. Maintenance guide and embedded model-invariant comments.

Defer larger work, such as a full modular rewrite or external data pipeline, to v15.
